# LiveCaption 实时配音方案：评审与改进计划

日期：2026-10-06。本文所有数字都在本机实测或从 CPA 日志统计得到。复测方法见第 6 节。

## 1. 原方案（2026-10-06 提出）

> 后端接 Edge-TTS（晓晓/云希）；前端做 Audio Ducking：配音播放时原声平滑降到 20%，结束后回到 100%；
> popup 增加「开启配音 / 音色 / 背景音量」；完全免费、无次数限制、全网视频网站通用；"比 YouTube Dubbing 更强"。

方向是对的：ASR、翻译、断句这三样 LiveCaption 都已经有了，只缺 TTS 和闪避。
但原方案默认配音能"跟得上画面"，实测下来跟不上。

## 3. 原方案的 5 个问题

### 问题 1：实时链路下配音一定滞后，而且越拖越久（最关键）

一句话说完后，要依次经过：VAD 等 0.3 s、ASR 约 0.1 s、翻译中位 1.5 s（慢的 3 s）、TTS 首包 1–2.4 s。
所以**一句话说完约 3–4.5 s 后中文才开始播，慢的时候约 6 s，走代理时还会更久**。

更大的问题是时长。中文配音比原声长约 40%，连续说话时配音队列只会越排越长：
一段 10 分钟不停顿的讲解，按 1.4 倍算会落后约 4 分钟。
就算全部加速 1.4 倍，也只能"不再继续变慢"，前面那 3–4.5 s 的固定延迟去不掉，画面和声音永远对不上。

YouTube Dubbing 并不是实时听写。它的核心是直接读视频自带的字幕：句子的起止时间事先已知，可以提前翻译、提前合成，
到了时间点准时播放。它对 YouTube、B 站无字幕视频的"AI 生成字幕"是付费功能，商店页没说是否实时；
对内置支持以外的网站，它要求把视频下载下来上传到服务器，处理完发邮件通知，明确不是实时的。
所以"在实时 ASR 后面直接接一个 TTS"做不出它那种效果。

### 问题 2：Edge-TTS 不是稳定的"免费无限制"

`edge-tts` 用的是 Edge 浏览器"朗读"功能的非公开接口，不是微软正式开放的服务。
实测直连 20% 失败，走代理 20%–50% 失败。微软随时可以收紧，开源社区也出现过它整体失效的时期。
它可以作为默认方案用，但必须准备：失败时直接跳过这一句、配好的音做缓存、可以切换到其他 TTS。

另外有一个值得放进计划的选项：**Azure 官方 TTS 免费层**，和 Edge-TTS 是同一批音色，每月约 25 万汉字，稳定，但需要注册账号拿密钥。

### 问题 3：只把音量压到 20% 盖不住原声

"保留背景音"的产品，通常会先用模型把人声和背景音分开，只压人声，背景音乐和音效保持原样。
只把整条音轨压到 20%，英文原声还清楚可辨，会和中文配音互相打架。
可以选的做法：
- 压到 5%–10%，接受背景音也一起变小；
- 只削弱人声所在的频段（大致 300 Hz–3.4 kHz），背景音保留得多一些，但效果有限；
- 真正做人声分离，CPU 上很难实时。

### 问题 4：音量闪避没有说在哪一层做

插件用 `tabCapture` 抓标签页声音时，Chrome 会把这个标签页本身静音，用户听到的声音其实是插件在后台重新播出来的那一路
（`offscreen.js` 第 59–61 行）。在页面里直接改 `<video>` 的音量，网站可能会改回去，
iframe 里的播放器、或用 Web Audio 出声的网站也管不到。
**闪避应该在 `offscreen.js` 重播的那一路上加一个音量节点（GainNode）来做。**
配音也从同一个地方播放，这样两者天然在同一条时间线上。

### 问题 5：几项说法会误导用户

- "全网通用"：只有实时听写模式是全网通用，而它有 3–6 s 的滞后。
- "无次数限制"：Edge-TTS 是非官方接口，没有任何保证。
- "比它更强"：实时性和准确度目前都比不上读现成字幕的方案。
- 另外有两项开销没算进去：当前翻译提示词是给日本影视剧写的（硬编码了一些术语），配音会把它的错误读出来，内容不对时比字幕更难忽略；
  其次每一句都会调用一次翻译和一次 TTS，CPA 的调用量会明显增加。

## 4. 改进后的方案：两种模式

### 模式 A：有字幕的网站（YouTube 等），读字幕提前配音，可以对齐画面

1. 在页面里读取播放器已经加载的字幕。只拦截播放器自己发出的字幕请求，不自己构造字幕地址；
   YouTube 已经对部分视频的字幕请求要求带一个由播放器生成的令牌（PoToken），自己构造的请求会拿到空内容。
   播放器只有在字幕打开时才会去请求字幕，所以插件需要自动打开字幕（可以不显示）。
2. 把字幕按句子合并（YouTube 自动字幕是一个词一个词出的，必须先合句）。
3. 带上前后文提前翻译后面 60–120 s 的内容，每批 20–40 句；同时按句子时间排期合成。
4. 播放时以 `video.currentTime` 为准，到点开始播配音；
   用户拖动进度条或暂停时，清空队列重新排期；视频变速时，配音一起变速。
5. 时长对齐的规则（参考你本机 `VideoLingo` 的配置）：
   - 配音不比原句长：正常播放；
   - 长出 20% 以内：加速播放（最多 1.2 倍）；
   - 加速后仍然超出：占用下一句开始前的空档（最多 1.5 s）；
   - 还是不够：让翻译重写成更短的句子；
   - 实在不行：把视频降到 0.9 倍速，或者暂停等配音读完。

### 模式 B：没有字幕的网站，实时听写后配音，接受滞后

1. 沿用现有的 VAD → ASR → 翻译流程。翻译完成后立刻合成，按顺序排队播放。
2. 控制排队长度：积压超过 4 s 就加速播放（最多 1.3 倍）；积压超过 8 s 就丢掉最旧的未播句子，只显示字幕，并在界面上提示"配音已跳过"。
3. 加一个"同传模式"开关：把视频降到 0.85 倍速播放，换取配音能跟上画面。
4. 界面上要写清楚："实时配音会比画面晚 3–6 秒"。

### 两种模式共用

- 后端合成之后，用二进制消息通过现有的 WebSocket 把音频发给 `offscreen.js`，在那里排队播放。
- 音量闪避：在重播那一路加 GainNode，压到 8% 左右；用 `setTargetAtTime` 做 80 ms 淡入、250 ms 淡出，避免爆音。
- 合成失败就跳过这一句，字幕照常显示，配音一律不重试，因为重试过的音频已经对不上画面了。
- 配好的音频缓存起来，key 是"音色 + 语速 + 文本"，重看同一段时直接用。
- TTS 设计成可替换：Edge-TTS（默认）、Azure F0（填了密钥就用）、本地 sherpa-onnx（离线兜底，本机没有 GPU，必须用小模型）。

## 5. 实施顺序（每一步都可以单独验收）

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 0 | 修 4 个现有问题 | 见下文 |
| 1 | 模式 B 的最小版本：配音、排队、音量闪避、失败跳过 | 一段 5 分钟的英文网课：配音不中断，积压不超过 8 s，没有爆音 |
| 2 | 加 Azure F0 和本地 TTS 作为备选 | 拔掉 Edge 能自动切换；Azure 每分钟最多 20 次请求，必须限流 |
| 3 | 模式 A 的 YouTube 版 | 有人工字幕的视频，配音开始时间和原句开始时间相差不超过 0.5 s |
| 4 | 模式 A 推广到 Bilibili / Udemy / Coursera | 每个网站单独验收 |

第 0 步要修的问题：

1. **时间戳单位错了**：`speech_segment.start` 是采样点数（16 kHz），后端却当成秒发给前端、写进逐字稿。
   实测：一句从第 2 秒开始的话，`start` = 37536（除以 16000 等于 2.35 s）。
   所以逐字稿里有"影片 40:00:32"这种时间，实际是第 9 秒。配音排期依赖这个时间，必须先修。
   另外，每次改设置都会重建 VAD，计数从 0 重新开始，修的时候要把开始位置一起累加进去。
2. **翻译超时**：现在 3.5 s 就放弃，实测 3% 的请求因此丢失；改成 6 s，并且只在超时时才降级到 Google 翻译。
3. **翻译提示词**：现在硬编码的是日本影视剧的术语，改成按场景切换的预设（影视 / 网课 / 新闻），作为配置项。
4. **VAD 上限写死**：代码把 `min_silence` 和 `max_speech` 限制为最多 0.3 s 和 4 s，用户在设置面板里调大也不起作用；
   改成尊重用户设置，默认值仍然是 0.3 s 和 4 s。
   （`max_speech` 不是硬上限：句子超过它以后，VAD 会临时提高判定门槛，促使句子尽早切开。
   设得太小，长句更容易在句中被切断，翻译和配音都会变差。模式 A 不经过 VAD，不受影响。）

## 6. 如何复测

```bash
cd ~/LiveCaption
venv/bin/python backend/bench_asr.py                                                  # ASR 解码耗时
~/.local/share/uv/tools/edge-tts/bin/python -u backend/bench_tts.py                   # TTS，直连
~/.local/share/uv/tools/edge-tts/bin/python -u backend/bench_tts.py http://127.0.0.1:7897   # TTS，走代理
```

翻译耗时：在 NAS 上从 CPA 的 `main.log` 里筛出 LiveCaption 的翻译请求（模型为 `gemini-3.1-flash-lite`），统计耗时分布。
